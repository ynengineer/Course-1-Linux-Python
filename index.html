Linux as your automation workstation

A Linux shell is the command interpreter on your automation computer. You already know Cisco EXEC and configuration modes; Bash instead runs programs and manipulates files. Running a command does not enter a universal configuration mode. Paths identify files, and your current directory affects relative paths.

Filesystem and paths

/ is the filesystem root. /home/student is this fictional user's home directory, abbreviated ~. Root the directory is different from root the privileged account. /etc commonly stores system configuration; /var/log holds logs. A leading slash makes a path absolute. backups/router.cfg is relative to your current directory. Linux names are case-sensitive.

Command Meaning Cisco connection
pwd Print current directory Know your working context
ls -la List details and hidden entries Inspect before acting
cd ~/automation Change directory Select your workspace
mkdir -p ~/automation/backups Create parents and directory Prepare a backup destination
cat devices.txt Print a small file Read a saved inventory
less router.cfg Page through a long file; q quits Similar purpose to paged show output
cp devices.txt devices.bak Copy without removing the original Preserve evidence
mv old.txt new.txt Rename or move Changes the path
man ls Open command documentation Like contextual help

Text and pipelines

grep selects matching lines. A pipe sends one program's standard output to another program's input. Unlike IOS filtering, it can join arbitrary programs. > overwrites or creates a file; >> appends. Inspect the destination before redirecting. wc -l counts newline characters.

mkdir -p ~/automation/backups
cd ~/automation
printf 'store001-rtr 192.0.2.11\nstore002-rtr 192.0.2.12\n' > devices.txt
cat devices.txt
grep store001 devices.txt
cat devices.txt | wc -l
cp devices.txt devices.bak

printf writes the two fictional inventory lines. The quotes keep the format string together and \n creates newlines. Neither address is a real course device. Do not type the $ prompt when copying commands.

Lab L01

In a disposable Ubuntu directory, create the automation workspace and a backups directory. Create the two-line inventory above, select only store001, copy the original to devices.bak and prove the inventory contains two lines. Inspect with pwd and ls. No sudo is required.

Hint: Create directories before changing into them. Use grep for selection and wc for counting.

Solution: Run the example block, then pwd, ls -la and wc -l devices.txt. Expected evidence: the path ends in automation, backups exists, devices.txt and devices.bak exist, and the line count is 2. Save your command transcript and explain why > could damage an existing file.

Administer the automation host safely

Your automation host has users, permissions, running processes and services. Think of this as maintaining the management plane that will reach your Cisco devices. Start by observing. A service restart can interrupt your own session or every automation job.

Users and permissions

whoami prints your username; id lists identity and groups. sudo runs an authorized command as another user, usually root. It is not needed for everyday project files. Use a dedicated automation account and scope privileges.

The three permission groups are owner, group and others. Read = 4, write = 2 and execute = 1. Thus 600 is owner read/write only; 700 also gives owner execute. On a directory, execute permits traversal, read lists names and write permits directory-entry changes when traversal is available.

whoami
id
mkdir -p ~/automation
cd ~/automation
touch lab-inventory.txt
chmod 600 lab-inventory.txt
ls -l lab-inventory.txt

touch creates an empty file or updates timestamps. chmod 600 changes its mode; it does not encrypt the file. Avoid using 777 as a permission workaround. File ownership and ACLs also affect access.

Services processes and logs

On Ubuntu with systemd, systemctl status ssh --no-pager inspects the SSH service. Some minimal containers do not run systemd; an unavailable service manager is not proof SSH is broken.

systemctl status ssh --no-pager
journalctl -u ssh -n 20 --no-pager
ps aux
df -h
free -h
ip address
ip route
ss -lnt

journalctl -u ssh filters logs to the SSH unit and -n 20 limits the result. Log visibility depends on permissions. ps shows processes, df filesystem capacity, free memory, ip interface and routing state, and ss -lnt listening numeric TCP sockets. These resemble show processes, show ip interface brief and show ip route in purpose, with different output.

Package administration

sudo apt update refreshes package metadata; it does not install all upgrades. sudo apt install openssh-client installs the SSH client on a disposable Ubuntu lab host. The client initiates sessions; openssh-server is only needed to accept inbound sessions. Plan actual patching and restarts separately. Read-only inspection comes before changes.

Lab L02

Create lab-inventory.txt and restrict it to the owner. Inspect identity, service state, recent SSH logs, disk capacity, interface addresses, routes and listening TCP sockets. A simulated service report is provided in Interactive Labs.

Hint: Permission digits are sums, not a decimal ranking. Use status and journal output before considering restart.

Solution: Use the command blocks above. Expected file mode: -rw-------. For the simulated case, SSH is active and listening on TCP 22; a failed login is an authentication issue. An active service alone does not prove a remote client can reach it. Record the evidence and one next diagnostic step. Do not restart SSH for this lab.

Begin with the SSH connection you already know

Next lesson • approximately 45 to 60 minutes • no completion recorded. Your SSH session to a C1111, C1101 or 2960X already automates transport and encryption. Network automation adds software that opens that session, sends commands, checks results and handles failures. Before writing that software, separate network reachability, server identity, user authentication and command authorization.

Client server and trust

The client initiates a connection; the server accepts it, normally on TCP 22. Your Ubuntu host is the client when connecting to a Cisco device. Running Ansible does not require an inbound SSH server on the controller merely to manage network devices.

A host key identifies the server. A user key authenticates you. They solve different problems. Your client records trusted host keys in known_hosts. A changed-host-key warning can indicate a legitimate rebuild or an attack. Stop and verify through a trusted separate channel before updating the record. ssh-keyscan collects a key but does not establish its trust.

First connection

All examples use documentation addresses and fictional accounts. These devices are simulated; do not expect the addresses to answer on the Internet.

ssh netauto@192.0.2.11
ssh -p 2222 netauto@192.0.2.11
ssh -vvv netauto@192.0.2.11

user@host selects the remote account and target. -p selects a nondefault port; it does not change the server's configuration. -vvv increases debugging. Redact usernames, addresses and sensitive data before sharing logs. On the Cisco side, VTY access lists, AAA, allowed transports, routing and algorithm support all affect the session.

Keys and permissions

On your disposable Linux controller, create a passphrase-protected user key:

ssh-keygen -t ed25519 -f ~/.ssh/netauto_lab -C netauto-lab
chmod 700 ~/.ssh
chmod 600 ~/.ssh/netauto_lab
ssh -i ~/.ssh/netauto_lab netauto@192.0.2.11

Use a unique filename; do not overwrite an existing key. The private file stays on the client; netauto_lab.pub is the public key. Provision the public key through an approved method. Linux servers commonly use authorized_keys; IOS and IOS XE public-key provisioning differs by release and AAA configuration. Ed25519 support on older Cisco images may be absent; verify supported modern algorithms before selecting an approved alternative. Do not globally enable obsolete algorithms to bypass an error.

ssh-agent can hold an unlocked key for a session. Agent forwarding exposes additional risk; it is not required for ProxyJump and is not part of this lab.

Jump hosts

A jump host provides a controlled path into a management network. Even with one target, it can centralize access restrictions and logging and avoid exposing the target directly. If the controller already has approved direct connectivity, a jump host may add no useful path.

ssh -J student@198.51.100.10 netauto@192.0.2.11

This makes an SSH connection to the jump host and forwards a TCP connection to the final target. Both host identities and both authentication steps matter. With a controller inside the management network, direct connectivity may be simpler.

A fictional OpenSSH client configuration:

Host lab-router
    HostName 192.0.2.11
    User netauto
    IdentityFile ~/.ssh/netauto_lab
    IdentitiesOnly yes
    StrictHostKeyChecking yes

Then ssh lab-router uses the alias. Strict checking requires a previously verified known_hosts entry. The filename ~/.ssh/config is OpenSSH configuration; it is separate from Ansible inventory.

OpenSSH libssh and Paramiko

OpenSSH is the command-line implementation used by ssh. libssh is a library; Ansible uses its Python binding ansible-pylibssh. Paramiko is a different Python SSH implementation. This course prefers libssh for network_cli and uses ansible_libssh_proxy_command for a jump path. These variables are taught in Lessons 8 and 9, not installed in this lesson.

ansible_connection: ansible.netcommon.network_cli
ansible_network_os: cisco.ios.ios
ansible_network_cli_ssh_type: libssh
# Optional jump path; verify both hosts before use
ansible_libssh_proxy_command: "ssh -W %h:%p student@198.51.100.10"

%h and %p become the destination host and port. OpenSSH ProxyJump settings and libssh proxy settings are not interchangeable by assumption. Installed Ansible and collection versions determine the accepted options; inspect ansible-doc in the actual environment.
